CFaC · v1.4

Conditional Formatting
as Code.

If your system's invariants are encoded in conditional formatting rules, they are the most-read documentation in your company. Treat them like infrastructure. Version them. Review them. Color them deliberately.

Why CFaC? See the workflow

The problem

In a typical SSaI deployment, the most important business logic is encoded not in formulas, not in Apps Script, and not in any documented system — but in conditional formatting rules. "Color this cell red if past_due. Color it yellow if outstanding more than 30 days. Color it green if active."

This logic is consequential. Every stakeholder reads it. The CFO makes decisions based on it. Customer success escalates on it. New hires learn the company by reading the colors.

And yet: it is invisible to source control, untestable, undocumented, and editable by anyone with the link. This is unacceptable. CFaC is the discipline of treating conditional formatting with the rigor it deserves.

The CFaC principles

  1. Rules are code. If it makes a business decision, it belongs in version control. Even if it lives in a sheet.
  2. Color has semantics. Green = passing. Yellow = degraded. Red = failing. No exceptions. No "I just liked the look of this purple."
  3. Every rule has a name. No anonymous formatting. Each rule is documented in a hidden tab called _cfac_rules.
  4. Rules are reviewed. Before merging a formatting change into the primary sheet, it must be reviewed in a copy and approved via comment thread.
  5. Rules are tested. Each rule has a corresponding row in _cfac_tests with example inputs and expected colors.

The CFaC workflow

A standard CFaC change looks like this:

1. Propose

# In _cfac_proposals tab, append a row:
rule_id:    cfac-0042
column:     Users!status
condition:  ISBLANK(status)
format:     background = #fff4e0, text = #b45309
author:     @naomi
rationale:  Empty status was indistinguishable from active. Now it is yellow.

2. Review

The on-call CFaC reviewer (rotation in the _cfac_oncall tab) inspects the proposal in a copy of the sheet. They check:

  • Does it conflict with an existing rule? (Run _cfac_lint.)
  • Does the color match SSaI's semantic palette?
  • Is the rationale defensible to a non-technical stakeholder?
  • Will it cause an existing customer's tab to suddenly turn red?

3. Test

The reviewer applies the proposed rule in a test copy and walks through _cfac_tests entries to confirm expected behavior.

# Test row example
rule_id:    cfac-0042
input:      "active"   # expect: no formatting
input:      ""         # expect: yellow
input:      "past_due" # expect: red (from cfac-0017)

4. Merge

The reviewer applies the rule to the production sheet and updates _cfac_rules with the merge timestamp and reviewer initials. A diff is emailed to the on-call list. Yes, by Apps Script. Of course.

5. Roll back (if needed)

If a rule causes a regression — for example, the CFO reports that "everything turned yellow at once" — the reviewer reverts via Google Sheets' version history. Documented retroactively in _cfac_incidents.

Anti-patterns

  • The Rainbow Sheet. Every cell a different color. No one knows what anything means. A failure mode.
  • The Aesthetic Override. "I made it pink because it looked nice." Pink does not appear in the CFaC palette.
  • The Inverted Convention. Red = good in some tabs, bad in others. Unforgivable. Promotes loss of trust.
  • The Untested Rule. Conditional formatting deployed to production without an entry in _cfac_tests. Forbidden by policy.
  • The Hidden Rule. A formatting rule whose condition references a cell on another tab via a stale name. Source of the worst incidents we have seen.

Adoption

In our internal study, teams that adopted CFaC saw a 38% reduction in time-to-detect for data quality regressions, and a 71% reduction in the phrase "why is this red?" being said in standup.

We strongly recommend pairing CFaC with Cell-Driven Design. Together they constitute a complete SSaI engineering discipline.
